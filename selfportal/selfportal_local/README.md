# SelfPortal — портал смены пароля локального пользователя Windows

Веб-приложение на IIS (ASP.NET Web Forms) для смены пароля локальной учётной
записи Windows Server, в том числе истёкшего. Разработано и доработано по
итогам пен-теста `https://detpit-as.esit.info:43445/SelfPortal/`.

## Файлы

| Файл | Назначение |
|---|---|
| `password.aspx` | Страница смены пароля (вся логика в inline-коде) |
| `web.config` | Заголовки безопасности + Secure cookie + скрытие версий |
| `deploy-selfportal.ps1` | Скрипт развёртывания на IIS (пул + приложение) |
| `README.md` | Этот файл |

> **Кодировка:** `password.aspx` и `deploy-selfportal.ps1` сохранены в
> **UTF-8 с BOM**. Это обязательно — Windows PowerShell 5.1 и ASP.NET
> читают файлы без BOM в системной ANSI-кодировке (Windows-1251), из-за
> чего кириллица ломается.

## Логика работы приложения

### 1. Инициализация страницы (`Page_Init`)

- В `Session["ViewStateUserKey"]` кладётся случайный GUID, который
  присваивается `ViewStateUserKey`. Это делается **до** обработки ViewState
  (в `Page_Init`, а не `Page_Load`) — защита от CSRF.

### 2. Загрузка страницы (`Page_Load`)

- **HTTPS-only:** если запрос не по HTTPS и не с localhost — редирект на
  `https://`-версию.
- **Блокировка по IP:** если IP в блокировке — форма скрывается, выводится
  сообщение о блокировке.
- **CAPTCHA:** определяется по счётчику неудач (`failCount >= CAPTCHA_THRESHOLD`).
  При первом открытии (не postback) и необходимости — генерируется CAPTCHA.

### 3. Определение IP клиента (`GetClientIP`)

- Используется только `Request.UserHostAddress`.
- **Намеренно игнорируются** `X-Forwarded-For` и `X-Real-IP` — им нельзя
  доверять без настроенного reverse proxy.

### 4. Счётчики неудач и блокировки

Два независимых уровня защиты от перебора:

| Уровень | Ключ кэша | Порог | Блокировка |
|---|---|---|---|
| По IP | `SelfPortal_Fail_<IP>` / `SelfPortal_Lock_<IP>` | `MAX_ATTEMPTS = 5` | 30 мин |
| По учётной записи | `SelfPortal_AcctFail_<user>` / `SelfPortal_AcctLock_<user>` | `MAX_ACCOUNT_ATTEMPTS = 10` | 60 мин |

- Блокировка по IP защищает от перебора с одного адреса.
- Блокировка по учётной записи защищает конкретный аккаунт от
  **распределённого** перебора (ботнет / ротация IP).
- Кэш — изолированный `new MemoryCache("SelfPortalCache")`, не общий
  `MemoryCache.Default`.

### 5. CAPTCHA

- Генерируется на сервере через `System.Drawing` (изображение с шумом и
  повёрнутыми символами), отдаётся как base64 data URI.
- Ответ хранится **только в Session**, в HTML попадает только картинка.
- **Одноразовая:** после проверки (успешной или нет) удаляется из Session.
- `CAPTCHA_THRESHOLD = 1` — включается после первой неудачной попытки.
- ГСЧ — криптографический `RandomNumberGenerator` (не `Random`).

### 6. Валидация имени пользователя (`IsValidLocalUsername`)

- Разрешены только локальные имена (латиница, кириллица, цифры, пробел,
  точка, дефис, подчёркивание), длина ≤ 64.
- **Запрещены** `\`, `/`, `@` — защита от доменных имён (`DOMAIN\user`,
  `user@domain`) и path traversal.

### 7. Проверка сложности пароля (`IsPasswordStrong`)

- Минимум 8 символов, обязательны: заглавная, строчная, цифра, спецсимвол.

### 8. Запрет смены пароля административных учёток (`IsAdministrator`)

- Проверка членства в группе «Администраторы» через
  `System.DirectoryServices.AccountManagement`.
- Группа ищется по **фиксированному SID `S-1-5-32-544`**
  (`BUILTIN\Administrators`), который не зависит от локализации Windows.
- **Почему не WinNT-провайдер:** `WinNT://./Administrators,group` падает на
  русской Windows («Не найдено имя группы» — группа называется
  «Администраторы»), а `WinNT://./S-1-5-32-544` не резолвит SID в пути.
  Поэтому используется `AccountManagement` + `IsMemberOf`.
- **Fail closed:** если проверка не удалась (исключение / группа не найдена) —
  учётка считается административной и блокируется. Ошибка пишется в Event Log.
- Проверка выполняется **до** проверки текущего пароля, чтобы форма не
  работала как оракул для админ-аккаунтов.

### 9. Смена пароля (`ChangeLocalPassword`)

- Повторяет рабочий PowerShell-сценарий через ADSI:
  `[ADSI]'WinNT://./<user>,user'` → `ChangePassword(old, new)`.
- Не используются `Username`/`Password`/`AuthenticationTypes.Secure`/
  `CommitChanges()` — только `Invoke("ChangePassword", args)`.

### 10. Обработчик кнопки (`btnChange_Click`)

Порядок проверок:

1. Блокировка IP.
2. Валидация имени пользователя.
3. Блокировка учётной записи.
4. **Запрет административных учёток** (см. п.8).
5. Заполненность всех полей.
6. Новый пароль ≠ текущий.
7. Сложность нового пароля.
8. Совпадение нового пароля и подтверждения.
9. CAPTCHA (если требуется).
10. Смена пароля.

### 11. Сообщения об ошибках (анти-перечисление)

- Для **всех** ошибок аутентификации (неверный логин, неверный пароль,
  административная учётка) пользователю показывается **одинаковое**
  нейтральное сообщение: «Неверное имя пользователя или текущий пароль».
- Это не даёт злоумышленнику отличить «учётка существует и она админ» от
  «учётки нет / пароль неверный» — защита от перечисления логинов.
- **В Event Log** при этом пишутся разные события (включая отдельное
  `Warning` о попытке смены пароля административной учётки) — аудит
  сохраняется, но наружу не утекает.

### 12. Логирование (`WriteLog`)

- Все события пишутся в **Windows Event Log → журнал «Приложение»**,
  источник **`RDWebPassChange`**.
- Типы событий: `Information` (успех), `Warning` (неудачная попытка,
  блокировка IP/аккаунта, попытка админ-смены), `Error` (исключения).
- Пароли **никогда** не пишутся в журнал.
- Ошибка записи журнала не ломает приложение (обёрнута в `try/catch`).

## Что исправлено в `web.config`

- `Strict-Transport-Security` (HSTS)
- `X-Frame-Options: DENY` (защита от clickjacking)
- `X-Content-Type-Options: nosniff`
- `Content-Security-Policy` (с `img-src data:` для CAPTCHA)
- `Referrer-Policy: no-referrer`
- `Permissions-Policy`
- `httpCookies requireSSL="true"` — флаг `Secure` на cookie сессии
- `enableVersionHeader="false"` — скрытие `X-AspNet-Version`
- `removeServerHeader="true"` — скрытие `Server` (IIS 10+)
- `customErrors mode="RemoteOnly"` — без утечки стек-трейса
- `requestFiltering` — ограничение размера запроса
- `defaultDocument` → `password.aspx` (без него IIS отдаёт 403 на `/SelfPortal/`)

## Развёртывание (`deploy-selfportal.ps1`)

Скрипт (запускать от администратора, сам повышает права):

1. Создаёт `C:\inetpub\wwwroot\SelfPortal`.
2. Копирует `password.aspx` и `web.config` из каталога скрипта.
3. Создаёт пул приложений `SelfPortal` (учётка **NetworkService**, .NET 4.0,
   Integrated).
4. Создаёт приложение `/SelfPortal` на `Default Web Site` (если существует —
   удаляет и пересоздаёт).
5. Перезапускает пул, проверяет результат, выводит итоговый URL.

Перед запуском задать в начале скрипта `$ClientName` и `$Port`.

> **Почему NetworkService:** у `ApplicationPoolIdentity` нет прав на чтение
> членства локальных групп, из-за чего проверка `IsAdministrator` падала.
> `NetworkService` имеет доступ к локальным учётным записям.

## Что осталось сделать вручную (не в коде)

1. **Удалить `iisstart.htm`** и дефолтный контент IIS.
2. **Закрыть `/RDWeb`** (RD Web Access), если он не нужен публично —
   IP-allowlist или VPN.
3. **Ограничить доступ к SelfPortal по IP** (allowlist корпоративных подсетей).
4. **Настроить алерты** на события `RDWebPassChange` (Warning/Error) в Event Log.
5. **Включить HSTS только после** того, как убедитесь, что сайт работает
   исключительно по HTTPS (иначе браузеры заблокируют HTTP-доступ).
6. **Обновить IIS/.NET** — заголовок `X-AspNet-Version: 4.0.30319` указывает
   на старый рантайм.

## Ограничения текущего решения

- CAPTCHA на `System.Drawing` — простая, но уже не читается из HTML. Для
  публичного портала лучше reCAPTCHA v3 / hCaptcha.
- Блокировка по IP держится на `Request.UserHostAddress`; при NAT один IP =
  много пользователей. Блокировка по аккаунту это компенсирует.
- Смена пароля по-прежнему требует только знание текущего пароля. Для
  административных учёток смена через портал запрещена полностью; для
  остальных при необходимости можно добавить второй фактор (код на
  email/телефон) перед сменой.
